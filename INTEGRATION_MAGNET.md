# Интеграция схемы этажей с 1С Магнит
Версия интерфейса 0.3.3, сборка №47. Контракт ниже предложен для интеграции с порталом; это не документация нативного API 1С Магнит.

## 1. Размещение и настройка
1. Получить актуальный index.html. Разместить только в согласованном внутреннем контуре, по HTTPS. Для SharePoint 2016 допустим самостоятельный внутренний сайт с Page Viewer / iframe или ссылка; на новом портале аналогично. Проверить CSP (inline script/style), frame-ancestors, корпоративную авторизацию и поддерживаемый браузер. Не ослаблять глобальные политики безопасности.
2. Создать серверный адаптер к кадровой ИС. Уточнить реальные URL, формат, метод авторизации, доступные поля, лимиты и правила доступа у владельца ИС. Если используется ключ, хранить его в серверном хранилище секретов под именем API_RG_MAGNET (предложенное имя, не требование 1С). Не передавать ключ в HTML, браузер, логи или репозиторий.
3. Реализовать три маршрута ниже на том же origin, с корпоративной сессией. Если портал размещён в подкаталоге, изменить base в конфигурации на согласованный путь; он должен вести к тому же origin. При отдельном хостинге схема и API-адаптер должны находиться на одном origin, с авторизацией пользователей.
4. В index.html найти строку:
```js
const RG_MAGNET_CONFIG=Object.freeze({enabled:false,base:'/api/rg-magnet',intervalMs:900000,demoFallback:false});
```
После готовности серверной части установить enabled:true. Интервал 900000 мс = 15 минут; изменить по необходимости. demoFallback:true разрешает демонстрационные записи при первой неудачной загрузке после подтверждения личности (только для пилота); для эксплуатации оставить false. При отказе в авторизации или невозможности подтвердить сессию реальные данные удаляются из интерфейса. Без API (enabled:false) показывается демонстрационный режим.

## 2. Предлагаемый HTTP-контракт
Все ответы: application/json, Cache-Control: no-store; HTTPS; обязательная проверка корпоративной сессии, не доверять роли из браузера. Ошибки: 401 без сессии, 403 при отсутствии прав, 503 при недоступности кадровой ИС. Не возвращать HTML-страницу авторизации вместо JSON. Не включать реальные данные в тестовый публичный репозиторий.

### GET /api/rg-magnet/session
```json
{"user_id":"user-demo-001","is_admin":true,"csrf_token":"<server-issued-token>"}
```
user_id — стабильный непрозрачный идентификатор текущего пользователя, is_admin — результат серверной проверки членства в согласованной группе администраторов. Для обычного пользователя false, CSRF-токен можно не возвращать. Токен привязан к сессии. При смене пользователя или роли интерфейс очищает текущий реестр.

### GET /api/rg-magnet/employees
Возвращать полный разрешённый пользователю снимок сотрудников, не отдельную страницу. Если источник использует пагинацию, собрать данные на сервере. Пример с вымышленными данными:
```json
{
  "updated_at": "2026-11-27T09:00:00Z",
  "employees": [
    {
      "employee_id": "demo-001",
      "is_active": true,
      "full_name": "Иванов Иван Иванович",
      "email": "ivanov@example.invalid",
      "position": "Специалист",
      "department": "Демонстрационное подразделение",
      "directorate": "",
      "phone": "",
      "birthday": "",
      "seat_code": "6.082",
      "visibility": "full"
    }
  ]
}
```
updated_at — время фактического получения снимка от источника (ISO 8601), не время чтения кеша. employee_id, is_active, full_name и уникальная корректная корпоративная email обязательны для активных видимых записей. Уточнить, как обрабатывать сотрудников без почты до промышленного запуска. Остальные текстовые поля необязательны, пустое место — seat_code:"". Формат seat_code согласовать с реестром рабочих мест и уточнённой нумерацией приёмных. Идентификатор сотрудника должен быть стабильным при смене ФИО и email.
Сервер применяет правила видимости: full — точное разрешённое место; floor — передать location_floor (число), не передавать seat_code; private — не передавать расположение; hidden — запись не возвращать обычному пользователю. Поля birthday/phone передавать только если разрешено корпоративной политикой; персональные данные минимизировать. Клиентские фильтры не являются механизмом защиты.
Уволенные сотрудники исключаются из снимка либо получают is_active:false. Дубли сотрудников (ID/email) и некорректный формат ответа отклоняют снимок. Неизвестные/некорректные и повторяющиеся места снимаются с отображения на схеме, сотрудники остаются доступны через поиск. Пустой успешный снимок employees:[] — действительный результат, не ошибка.

### POST /api/rg-magnet/refresh
Администратор нажимает «Обновить данные сейчас». Запрос с корпоративной сессией и X-CSRF-Token, JSON body {}. Проверить роль и CSRF на сервере, ограничить частоту и параллельность, запросить актуальные данные у источника (не просто прочитать старый кеш), обновить серверный снимок и вернуть JSON того же формата, что GET /employees. При сбое вернуть ошибку; не выдавать старый снимок как новый. Клиент прекращает ожидание каждого запроса через 30 секунд; для долгих операций потребуется согласованный асинхронный контракт и доработка клиента. Обычным пользователям POST запрещён. GET можно обслуживать из централизованного кеша со сроком обновления до 15 минут, чтобы каждый браузер не нагружал 1С напрямую.

## 3. Администрирование и хранение
- В демонстрации скрытая точка входа: index.html?admin=1 (старый демонстрационный пароль; не защита).
- При enabled:true пароль демонстрации не используется; кнопка в подвале появляется только после ответа session.is_admin=true. Все реальные полномочия проверять на сервере.
- В админ-панели «Интеграции»: статус, диагностика мест, время снимка, проверка подключения и принудительное обновление.
- Кадровый реестр в рабочем режиме только для чтения; ручной импорт/редактирование отключены. Запись кадровых данных — в 1С Магнит по согласованному процессу.
- История последних 10 выбранных сотрудников хранится в sessionStorage по идентификатору пользователя (только ID, без ФИО), в рамках вкладки. При новом снимке недоступные записи исключаются. Для истории между устройствами нужен отдельный серверный API.
- Последний успешный снимок хранится в памяти вкладки, не в localStorage. При временной ошибке источника после подтверждения той же сессии отображается снимок с предупреждением.
- Редактор планировки пока локальный: постоянное общее сохранение и авторизацию изменений реализовать отдельно. Обращения об ошибках требуют корпоративного адаптера OfficeMap.configureReports; в рабочем режиме локальная отправка заблокирована, пока он не подключён. Не использовать публичный GitHub для реальных персональных данных или несогласованных внутренних планов.

## 4. Приёмочные сценарии
- Демонстрация без API, поиск тестовых сотрудников, обычный URL без кнопки админки, URL ?admin=1 с демонстрационным входом.
- Успешная сессия обычного пользователя: реальные карточки и поиск, отсутствие админ-кнопки; повторное открытие сотрудника перемещает его в начало истории; не более 10 записей.
- Сессия администратора: кнопка видна, раздел «Интеграции», GET-проверка и POST-обновление без ожидания 15 минут.
- Обновление снимка по таймеру, повторный запрос во время уже запущенного не дублируется; во время редактора планировки обновление отложено.
- Пустой снимок, сотрудники без мест, несуществующие и повторяющиеся места, увольнение, смена ФИО/email.
- Пропажа связи после успеха: предупреждение о неактуальных данных; 401/403 или неподтверждённая сессия: очистка данных и скрытие админки.
- Сервер: отказ POST для рядового пользователя, отказ при неверном CSRF, отсутствие ключей и запрещённых полей в сетевых ответах.
- Проверить в целевом браузере и реальном портале, в том числе iframe/SSO. Промышленную эксплуатацию начинать только после согласования ИБ и владельца кадровой ИС.
